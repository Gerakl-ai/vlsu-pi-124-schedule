## Проверенные находки

### Повторная проверка происхождения, 23 сентября

Опубликованный `data/status.json` завершён 22 сентября в 21:38:34 UTC:
966 попыток, 0 успешных расписаний, 966 ошибок. Это не показатель количества
ранее сохранённых снимков. Опубликованный снимок ПИ-124 по-прежнему содержит
`capturedAt: 2026-09-08T09:29:13.535Z` и `provenance: null`.

Найдено ошибочное присваивание происхождения в панели настроек:
`schedule.provenance ?? status.provenance` связывало старый снимок с последним
обходом, даже когда тот не получил ни одного расписания. Убрано: сведения
о снимке и последнем обходе показываются раздельно. Отсутствие метаданных
не объявляется доказательством ручной сборки. Ссылка на коммит сборщика
больше не называется коммитом с данными: это разные артефакты.

Эффект загрузки отчёта зависел от собственного состояния `loading`, что
прерывало начатый запрос и могло запускать повторные запросы. Теперь один
запрос на открытие панели, ограничение 8 секунд, отмена при закрытии без
повторного цикла. Браузерный тест `scripts/qa-provenance.cjs` проверяет
раздельное происхождение, один запрос, HTTP 503 без цикла. В этом тесте SW
отключён для контролируемого перехвата HTTP; это не проверка SW-стратегии.

- Приложение доступно по двум разным origin: germanpolkin.ru и workers.dev. IndexedDB `lad-personal` и localStorage не переносятся между ними. Пустой список на новом адресе не доказывает удаления базы на старом. Удаление установленного приложения и очистка данных сайта запрещены как рекомендации до попытки экспорта.
- Подгруппы искусственно переставлялись на знаменателе в `src/lib/subgroup.ts`. Одинаковые строки двух недель не доказывают чередования. Эта эвристика удалена, порядок источника сохранён; регрессия закреплена тестом.
- Service worker удалял все CacheStorage-кэши origin при активации. На домене с несколькими приложениями это нарушает изоляцию. Кэш теперь именуется с базовым путём, очистка ограничена своим пространством, чтение также ограничено текущим кэшем. Старые неоднозначные кэши сохранены.
- Опубликованный Worker health возвращает `release: dev`, а HTML Pages содержит старую метку `2026.09.16.2`. Версии в HTML, JS и Worker требуют единого build ID; метка HTML сейчас непригодна как доказательство актуальности.

- Восстановление запуска учитывает подкаталог Pages, сохраняет выбранную группу и не снимает регистрации соседних приложений. HTML получает build ID сборки. - Резервная копия версии 6 переносит пользовательские папки и цвета; версии 1–5 читаются. Проверка через мобильный интерфейс: импорт, перезагрузка и экспорт сохраняют запись, HTML-форматирование и папку. Черновики в резервную копию пока не входят. Исходные пропавшие записи пользователя не восстановлены и остаются отдельным открытым пунктом.

Поддержку BASE_URL, статический сбор расписания, отказ перезаписывать валидные снимки пустым ответом, каталог форм обучения, происхождение снимков и локальное резервирование. Полный откат уничтожил бы полезную работу. Изменения принимаются по отдельности после проверки.

## Следующий порядок работ

1. Проверить старый установленный контекст и экспорт записей существующим механизмом. Импортировать файл на выбранном адресе. Сервер и новый домен не могут извлечь локальную базу другого origin. Не обещать восстановление удалённой базы без резервной копии.
2. Проверить обновление старого service worker на новую сборку, зависание модулей, восстановление без сети, сохранность заметок и черновиков. Отдельно проверить корень Worker и подкаталог Pages.
3. Согласовать один основной адрес. Pages пригоден для статических снимков; Worker сохраняет ценность для обновлений по запросу. Не делать принудительный redirect до экспорта локальных данных.
4. Унифицировать build ID и происхождение данных. Проверить реальный отчёт обхода и несколько групп разных институтов; старые сведения о количестве групп и недоступности API не считать текущими замерами.
5. Проверить ограничения по учебным неделям, подгруппы, сессию и каникулы на подтверждённых примерах. Не синтезировать занятия из предположений.
6. Упростить главный экран: дата, текущая/следующая пара, список; статистику и оформление перенести в дополнительные действия. Сохранить явные подписи и состояние актуальности без высокого баннера.
7. Доработать десктоп и landscape, клавиатуру редактора, доступность, контраст и уменьшение движения. Проверить iPhone и Android на реальных устройствах, а не объявлять эмуляцию эквивалентной.
8. Подготовить пилот: несколько групп разных институтов, журнал дефектов, документация развёртывания и обработки данных, выбор лицензии правообладателем. Обсудить с ИТ-службой официальный источник и допустимую нагрузку до расширения обхода.

## Критерии готовности к массовому запуску

### Запуск и локальная база: проверка 22 сентября

Исправлены независимость ранней проверки зависания от основного JavaScript,
встроенная версия service worker и полный список файлов офлайн-сборки.
Новая версия активируется только после загрузки всех перечисленных файлов;
восстановление не удаляет старый кэш заранее. Проверены оба опубликованных
адреса: зависшие JS/CSS-запросы, обновление через прежний URL воркера,
повторный запуск офлайн. Это браузерные проверки, не доказательство
восстановления конкретного установленного приложения пользователя на iPhone.

Открытие IndexedDB ограничено 1,5 секунды, заблокированное обновление базы
сразу переводит чтение на имеющуюся локальную резервную копию. Запоздалое
соединение закрывается, обновление версии базы не удерживает открытые
соединения. При объединении копий записей время сравнивается по timestamp,
а не лексикографически: разные часовые пояса больше не подменяют свежую
запись старой. Проверены зависание, блокировка и поздний ответ базы.

Остаются риски: если одновременно отказали оба хранилища, запись может
ошибочно выглядеть сохранённой; удаления без tombstone могут восстанавливаться
из второй копии; зависание транзакции после успешного открытия базы требует
отдельной защиты. Эти случаи не считаются исправленными данным изменением.
Нельзя утверждать, что прежние записки пользователя восстановлены: доступ
к их исходному контексту на устройстве всё ещё не подтверждён.

### Открытый дефект: ограничения по учебным неделям

Проверено 22 сентября: `selectDayLessons` в `src/lib/time.ts` учитывает чётность, день недели и точную дату сессии. Условия в тексте `(с 10 по 16 нед)` не учитываются. В текущем снимке ПИ-124 такие условия есть, поэтому подсчёт занятий, календарь и ближайшая пара могут включать занятие вне своего периода.

Официальная публикация https://www.vlsu.ru/novosti-i-sobytija/novost/news/den-znanii-vlgu-2026-programma-meroprijatii подтверждает начало года по числителю и смысл двух половин ячейки. Она не подтверждает единый календарь нумерации недель семестра для всех форм обучения. Нельзя выводить номер недели весеннего семестра или заочников из одной только чётности.

Для исправления нужны: подтверждённая дата первой учебной недели и границы семестра по группе/форме, происхождение календаря, разбор ограничений отдельно для каждого варианта занятия. Один селектор применимости должен использоваться в Сегодня, Неделе, календаре, ближайшей паре, уведомлениях и экспорте. Неоднозначное условие сохраняется в исходном виде с признаком непроверенности, а не молча превращается в отсутствие занятий. Регрессии: включённые обе границы диапазона, «с N», «по N», смешанные варианты подгрупп, переход семестра и сессия.
