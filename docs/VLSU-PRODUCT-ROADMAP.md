# Лад ВлГУ: аудит и план превращения в университетский продукт

Дата аудита: 15 сентября 2026 года.

## Решение в одном абзаце

Проект уже сильнее обычного студенческого прототипа: есть PWA, мгновенный запуск из локального кэша, proxy к нестабильному API ВлГУ, edge/KV-снимки, заметки и адаптация под телефон. Для массового запуска нужно не копировать приложение для каждой группы, а превратить его в один мультигрупповой продукт с выбором института и группы, версионированными снимками данных и спокойным интерфейсом. Исходный код следует открыть на GitHub, а production оставить на Cloudflare Workers либо перенести на инфраструктуру ВлГУ. GitHub Pages может хранить только статический frontend и сам по себе не заменяет proxy, cron и KV.

## Что исправлено в текущем цикле

- Тип недели теперь привязан к дате получения `CurrentWeekType`. Старый снимок корректно переключается на следующую неделю даже без ответа ВлГУ.
- Дата снимка типа недели отделена от даты снимка расписания, поэтому смешанный ответ `current info live + schedule cache` не переворачивает неделю ошибочно.
- День занятия определяется по названию дня, а не по позиции элемента в массиве API.
- Пустой HTTP 200 от ВлГУ больше не считается хорошим снимком и не перезаписывает edge/KV-кэш.
- Офлайн-статус сокращён до одной строки; на телефоне дублирующее название института в нижней строке шапки скрыто.
- На узком экране убрана декоративная бегущая строка, повторявшая сведения из карточек ниже.
- API-адаптер больше не привязан к одному `Nrec`: расписание загружается для выбранного `GroupProfile`.
- Первый запуск получил двухэтапный выбор института и группы с поиском и локальным кэшем каталогов.
- Расписания разных групп хранятся раздельно; старый снимок ПИ-124 копируется в новую схему без удаления исходного ключа.
- Worker регистрирует только группы, для которых получил валидное расписание, и прогревает ограниченный список недавно активных групп.
- Ручной выбор числителя или знаменателя больше не переворачивается повторно при переходе на соседнюю неделю.
- Приложение получило нейтральную иконку «Лад ВлГУ», а группа и институт представлены отдельным динамическим знаком внутри интерфейса.

## Текущее состояние

### Сильные стороны

- Cache-first UI: пользователь сразу видит последнее полезное расписание.
- Три уровня устойчивости: локальное состояние, Cloudflare Cache API, глобальный KV-снимок.
- Семантическая нормализация занятий, подгрупп, преподавателей, аудиторий и экзаменов.
- PWA, service worker, installable режим и адаптивный интерфейс.
- Локальные заметки и резервная копия без обязательной регистрации.
- CI, typecheck, unit-тесты и проверяемый release endpoint.

### Ограничения перед массовым запуском

- Ссылка пока не кодирует выбранную группу, нет избранных групп и быстрого переключения между ними.
- Личные заметки ещё не имеют явной области группы, поэтому предметные связи нужно изолировать до мультигруппового пилота.
- `App.tsx` и `styles.css` слишком крупные; изменение одного экрана повышает риск регрессий на другом.
- Каталоги кэшируются на устройстве, но ещё не имеют формального versioned server-side контракта и панели свежести.
- Нет наблюдаемости качества данных: нельзя быстро увидеть, какие группы давно не обновлялись.
- Нет формализованной лицензии, правил вклада, политики безопасности и архитектурных решений.
- Интерфейс показывает несколько одинаковых показателей одновременно и иногда требует догадаться, является элемент кнопкой или статусом.

## Целевая архитектура

```text
GitHub public repository
  -> GitHub Actions: lint, typecheck, tests, build, Worker dry-run
  -> Cloudflare Worker + static assets
       -> /api/catalog: институты и группы
       -> /api/schedule/:groupId: валидированный снимок
       -> Cloudflare Cache API: быстрый edge-ответ
       -> KV: последний успешный глобальный снимок
       -> VLSU API: источник свежих данных
  -> PWA IndexedDB: последние выбранные группы, расписания и личные заметки
```

### Почему не чистый GitHub Pages

GitHub Pages является статическим хостингом HTML/CSS/JS. Для текущего продукта отдельно всё равно потребуются proxy к ВлГУ, фоновое обновление, общий снимок и серверный AI endpoint. Разделение frontend на Pages и backend на другом домене добавит CORS, два deployment pipeline и более сложное восстановление PWA без функциональной выгоды.

Рекомендуемая схема:

1. GitHub остаётся открытым источником правды, местом code review, CI, issues и релизов.
2. Cloudflare Workers остаётся исполняемой платформой до появления официальной инфраструктуры ВлГУ.
3. Production получает нейтральный домен, затем официальный поддомен вроде `schedule.vlsu.ru`.
4. Для полной независимости от одного поставщика описывается adapter интерфейс хранения; KV можно заменить S3/PostgreSQL/Redis без изменения клиента.

GitHub Pages допустим только как публичный demo frontend или страница документации, подключённая к тому же Worker API.

## Модель данных

### Каталог

```ts
type Institute = {
  id: string;
  name: string;
  shortName: string;
  visualKey: string;
};

type StudyGroup = {
  id: string;        // внутренний стабильный id приложения
  nrec: string;      // идентификатор API ВлГУ
  name: string;
  course: number;
  instituteId: string;
  active: boolean;
};
```

### Снимок расписания

```ts
type GroupScheduleSnapshot = {
  schemaVersion: number;
  group: StudyGroup;
  semester: number;
  lessons: LessonSlot[];
  weekType: 1 | 2;
  weekTypeAsOf: string;
  scheduleFetchedAt: string;
  source: "live" | "edge-cache" | "global-snapshot" | "device-cache";
  contentHash: string;
};
```

Критически важно хранить отдельно время получения расписания и время, к которому относится тип недели. Снимок заменяется только после структурной и семантической валидации.

## Стратегия надёжности API

1. Устройство немедленно показывает последний снимок выбранной группы из IndexedDB.
2. Worker отвечает свежим валидным результатом либо последним валидным снимком.
3. Ответы `200` с пустой строкой, пустым массивом в учебный период или повреждённой схемой не заменяют хороший снимок.
4. На клиент возвращаются `source`, `snapshotAt`, `age`, `contentHash` и диагностический request id.
5. Обновление всех групп не запускается одним cron-залпом: популярные группы прогреваются по расписанию, остальные лениво после запроса.
6. При росте нагрузки cron создаёт небольшие задания в очереди с ограничением параллелизма и backoff, чтобы не усиливать сбой API ВлГУ.
7. Для каждой группы ведутся `lastSuccessAt`, `lastAttemptAt`, причина ошибки и возраст снимка без хранения персональных данных студентов.
8. Администратор видит dashboard качества: доля групп со свежими данными, p95 ответа, пустые payload и расхождения схемы.

## Пользовательский сценарий для всех групп

### Первый запуск

1. Поле поиска сразу ищет одновременно по институту и группе.
2. После выбора приложение сохраняет группу локально и открывает сегодняшний день.
3. Пользователь может добавить ещё группы в избранное, но одна остаётся основной.
4. Группой можно поделиться ссылкой или QR-кодом: `/g/pi-124`.
5. Последние группы доступны без сети.

### Ежедневное использование

- Главный экран: дата, текущая/следующая пара, короткий статус свежести и список дня.
- Экран недели: дни и занятия, переключение недели и календарь.
- Записи: личный слой поверх расписания, по умолчанию только на устройстве.
- Настройки: группа, уведомления, внешний вид, данные и диагностика.

Переключение группы размещается в шапке как понятная команда с названием и стрелкой. Обновление данных получает отдельную иконку и не маскируется под переключатель недели.

## Упрощение интерфейса

### Оставить в первом viewport

- выбранную группу;
- дату и быстрый переход к календарю;
- текущую или следующую пару;
- список сегодняшних занятий;
- один компактный индикатор актуальности.

### Убрать или спрятать глубже

- повтор одного и того же количества пар в трёх блоках;
- декоративные бегущие показатели, конкурирующие с содержанием;
- технические слова `cache`, `snapshot`, `API` из обычного режима;
- постоянно анимирующиеся эффекты за текстом;
- управление, смысл которого понятен только после эксперимента.

### Правила взаимодействия

- Кликабельное выглядит кликабельным: кнопка имеет иконку, подпись либо стрелку перехода.
- Статус не выглядит кнопкой.
- Основное действие на экране одно; вторичные действия уходят в меню.
- Детали пары раскрываются по нажатию без сдвига соседних строк.
- Анимации объясняют переход и укладываются примерно в 180-260 мс; бесконечное движение отключается при энергосбережении, фоне и `prefers-reduced-motion`.
- Минимальная зона нажатия 44x44 CSS px, контраст и фокус проверяются автоматически.

## Визуальная система и иконки

Не нужно вручную рисовать отдельную картинку для каждой группы: это плохо масштабируется и создаёт визуальный шум.

- Одна самостоятельная иконка продукта `Лад ВлГУ`, не содержащая номер конкретной группы.
- Один visual token set на институт: акцент, спокойный паттерн, короткая аббревиатура и факультативный утверждённый символ.
- Группа получает детерминированный badge из названия и курса, например `ПИ / 124`, поверх стиля института.
- Любые официальные гербы, логотипы и названия используются только после письменного согласования с ВлГУ.
- Светлая и тёмная темы сохраняют одну и ту же информационную иерархию; тема не меняет смысл цветов ошибок, текущей и прошедшей пары.

## Открытость и доверие

Перед демонстрацией руководству репозиторий должен содержать:

- `LICENSE` после решения ВлГУ о модели распространения;
- `CONTRIBUTING.md`, `CODE_OF_CONDUCT.md`, `SECURITY.md`;
- схему архитектуры и ADR с обоснованием Cloudflare;
- документированную схему данных и правила валидации;
- публичный changelog и воспроизводимый build;
- перечень внешних сервисов и точное описание, какие данные куда уходят;
- privacy notice внутри приложения;
- отдельные demo-данные для скриншотов и разработки;
- issue templates для ошибки расписания с группой, датой и request id, без личных заметок.

Для официального внедрения полезнее прозрачный репозиторий и воспроизводимый pipeline, чем конкретный статический хостинг.

## Приватность и безопасность

- Расписание является публичным учебным контентом, но личные заметки не должны попадать в телеметрию и логи.
- AI-классификация остаётся opt-in с понятным согласием и локальным режимом по умолчанию.
- Если появится синхронизация заметок, потребуются аккаунт, шифрование, удаление данных и отдельная правовая оценка.
- Proxy разрешает только известные маршруты, ограничивает размер тела и частоту запросов.
- CSP, dependency audit, secret scanning и CodeQL входят в CI до пилота.
- Административный dashboard закрывается SSO ВлГУ/Cloudflare Access.

## План работ

### Этап 0. Стабилизация PI-124, 1 неделя

- завершить исправление типа недели и защиты снимков;
- добавить интеграционный fixture с реальными вариантами ответа API;
- проверить iPhone 16 Pro, Android Chrome, standalone и browser mode;
- зафиксировать UX-аудит и убрать дублирующие блоки;
- разделить `App.tsx` и CSS по экранам без изменения поведения.

Критерий: семь дней использования без неверного дня недели, потери кэша и критических визуальных регрессий.

### Этап 1. Мультигрупповое ядро, 2 недели

- убрать `PI-124` и `Nrec` из доменной логики;
- создать каталог институтов/групп и selector первого запуска;
- мигрировать local cache на ключи `schedule:v2:<groupId>`;
- поддержать избранные и смену основной группы;
- параметризовать Worker и тесты минимум на три института и десять групп.

Критерий: любая активная группа из каталога открывается по прямой ссылке и остаётся доступной офлайн после первого успешного получения.

### Этап 2. Надёжная платформа данных, 2 недели

- ввести versioned snapshot contract и content hash;
- добавить lazy refresh, очередь, backoff и лимиты на upstream;
- исключить пустые/повреждённые ответы из хороших снимков;
- сделать dashboard свежести и структурированные логи без личных данных;
- добавить ручной quarantine для ошибочного снимка.

Критерий: падение API ВлГУ не делает установленное приложение бесполезным и не распространяет пустой снимок новым устройствам.

### Этап 3. Product UX и доступность, 2 недели

- новый onboarding и быстрый поиск группы;
- упрощённые Today/Week без повторов;
- понятный статус актуальности и диагностический экран;
- WCAG 2.2 AA для основных сценариев;
- performance budget для слабых Android-устройств и отключение тяжёлых эффектов в фоне.

Критерий: новый пользователь без подсказок находит группу и сегодняшнюю пару менее чем за 30 секунд.

### Этап 4. Открытый пилот, 2-4 недели

- оформить репозиторий, документацию, security policy и лицензию;
- провести пилот на 5-10 группах разных институтов;
- собрать только агрегированные показатели надёжности и добровольную обратную связь;
- устранить ошибки данных, подготовить поддержку и регламент инцидентов;
- получить согласование бренда и официального домена.

Критерий: минимум 95% открытий показывают полезное расписание сразу; отсутствуют подтверждённые случаи потери локальных заметок.

### Этап 5. Демонстрация ректору

- трёхминутный сценарий: выбор группы, мгновенное расписание, отключение сети, сохранённый снимок, заметка к паре;
- одностраничная схема архитектуры и данные пилота;
- прозрачный репозиторий, CI и список известных ограничений;
- варианты владения: студенческий open source, совместная лаборатория или официальный сервис ВлГУ;
- бюджет эксплуатации, ответственные и план переноса на инфраструктуру университета.
